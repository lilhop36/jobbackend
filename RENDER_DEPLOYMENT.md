# Render Deployment

This repository includes `render.yaml` for a Render Blueprint containing:

- one Node.js web service rooted at `backend/`;
- one Render PostgreSQL database;
- Prisma Client generation during build;
- `prisma migrate deploy` before each deploy;
- HTTP health checks at `/api/health`;
- secrets declared as unsynchronized environment variables.

## Deploy

1. Push this repository to GitHub.
2. In Render, choose **New → Blueprint**.
3. Select `lilhop36/jobbackend` and the `master` branch.
4. Review the generated resources before applying the Blueprint.
5. Enter `GROQ_API_KEY`, `NVIDIA_API_KEY`, and/or `MISTRAL_API_KEY` manually when prompted. Do not commit these values.
6. Apply the Blueprint and wait for the first migration and deploy to complete.

The Android API base URL will be:

```text
https://jobhunter-ethiopia-api.onrender.com/api/
```

Render may assign a different service name or URL if the name is already taken. Use the actual URL shown in the Render dashboard.

## Database strategy

Production uses PostgreSQL and the committed initial migration in `backend/prisma/migrations/20261109164500_init_postgresql/`. Deployments use `prisma migrate deploy`; they do not use `prisma db push`.

Local development retains SQLite in `backend/prisma/schema.sqlite.prisma`. Use:

```bash
cd backend
pnpm prisma:generate:sqlite
pnpm prisma:push
pnpm build
pnpm start
```

The production schema is `backend/prisma/schema.prisma` and is generated by the Render build command.

## Free-tier limitations

Render documents that free web services spin down after 15 minutes without inbound traffic, require roughly one minute to wake, and have ephemeral filesystems. Therefore SQLite is not used for production.

Render’s free PostgreSQL has a fixed 1 GB capacity, no backups, may be restarted for maintenance, and expires 30 days after creation. After expiration, there is a 14-day grace period to upgrade before deletion. This is appropriate for testing or a short-lived demo, not durable production. Upgrade PostgreSQL before the expiration date or move the database to another managed provider.

The Blueprint disables the in-process periodic sync on Render (`ENABLE_PERIODIC_SYNC=false`) to prevent duplicate workers if the service is later scaled. The initial sync runs once when the service starts (`AUTO_SYNC=true`). For recurring production ingestion, use a separate paid Render Cron/Worker or an external scheduler that calls `POST /api/sources/sync`.
